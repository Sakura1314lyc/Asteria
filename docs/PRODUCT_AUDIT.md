# 产品审计与补强记录

本文件记录 Paper Research Workbench 从研究内核走向可长期使用产品时发现的问题、依据和处理状态。每次进入新的大功能阶段，应先重新检查相关后端、数据模型、API、测试与安全边界，再更新本表。

> 本文件按时间保留审计轨迹。早期章节中的“暂无”与“下一阶段”是当时快照；判断当前能力时，以 README、路线图和靠前的最新审计为准。

## 2026-08 研究方案修订、API 最小响应与动态反馈复审

### 新增依据

- [PRISMA-P checklist](https://www.prisma-statement.org/s/PRISMA-P-checklist.pdf)：系统综述方案发生重要修订时，应说明并记录修订内容及理由。
- [PRISMA 2020 expanded checklist](https://www.prisma-statement.org/s/PRISMA_2020_expanded_checklist-yc78.pdf)：已注册方案之后的变更需要报告，并解释每项变更的理由。
- [OWASP API excessive data exposure](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/12-API_Testing/03-Testing_for_Excessive_Data_Exposure)：API 应在服务端挑选业务需要的字段，不能返回完整内部对象再依赖客户端过滤。
- [W3C 状态消息技术](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA19)：异步成功、加载与错误反馈需要以无需夺取焦点的状态/警报语义通知辅助技术。

### 原项目复查与处理

| 级别 | 问题 | 风险 | 处理 |
|---|---|---|---|
| P0 | `ReviewProtocol` 可被覆盖，但没有变更原因和历史事件 | 检索范围被事后改变时无法还原研究决策 | 实际字段变化必须填写理由，服务端保存字段级 before/after 与 `protocol_updated` 事件 |
| P0 | 运行、健康检查和作业响应直接序列化内部对象 | 暴露 SQLite、数据根目录、运行目录或后台返回值 | 新增显式 `public_run` / `public_job`，健康检查只报告存储类型 |
| P1 | 项目事件存在于详情 API，但前端没有呈现 | 审计数据对研究者不可见，无法用于日常复核 | 项目概览新增连续修订账本，合并展示项目身份与方案修订 |
| P1 | 若干异步错误和加载文本没有 live-region 语义 | 屏幕阅读器用户不知道操作已完成或失败 | 通用加载使用 `role=status`，错误使用 `role=alert`，成功使用礼貌播报 |
| P1 | 方案字段较多，直接铺在概览页会稀释研究主线 | 页面重新变成通用后台表单墙 | 修订器进入受控 modal，按资格边界与结构化范围分组，概览只保留摘要 |

### 验收结论

隔离数据库内完成“项目资料修改 → 方案修订并填写原因 → 审计账本断言 → 文档/对话/运行/项目删除”。API 黑盒断言响应不包含测试根目录、`run_dir`、`data_root`、数据库路径或作业 `result`；浏览器排练同时覆盖 375px、横屏、放大字体、无横向溢出和 reduced-motion。公共观测站只展示明确标注为合成样例的修订记录，仍在服务端拒绝 mutation。

## 2026-08 项目生命周期、级联清理与误操作复审

### 原项目复查结论

原数据模型已有大部分 SQLite 外键级联，但“数据库记录消失”不等于删除完整：全文 FTS5 条目、运行与项目磁盘目录、孤立论文记录仍可能残留；前端也缺少项目资料修改、模型连接修改和细粒度删除入口。删除活跃运行还会破坏后台任务与数据库状态的一致性。

| 级别 | 问题 | 风险 | 处理 |
|---|---|---|---|
| P0 | 仅依赖外键级联，FTS5 与受管磁盘不在同一清理语义中 | 搜索命中已删除全文，或磁盘持续残留研究材料 | 为项目、运行和文档增加显式 FTS/磁盘清理；路径必须是数据根目录下的精确子目录 |
| P0 | 活跃项目或运行可以进入删除流程 | 后台线程写入已删除状态，产物和数据库分叉 | `queued` / `running` 状态服务端返回冲突，前端同步禁用并解释原因 |
| P0 | 项目身份可变但没有历史 | 研究问题或综述类型被修改后难以审计 | schema 升级到 v6，新增 `project_events` 保存字段级 before/after |
| P1 | 危险按钮缺少对象绑定式确认 | 用户可能在相似项目、文件或运行之间误删 | 项目、运行、全文、对话和论文分别要求输入名称、文件名或稳定 ID |
| P1 | 删除最后一份全文后论文仍显示“已取得” | 状态与实际文件矛盾 | 删除文档后检查剩余关联，必要时重置全文获取状态 |
| P1 | 删除后立即失效活跃查询 | React Query 观察者可能重新请求已删除资源并产生 404 | 删除前取消对象查询，先完成路由/选择切换，再刷新父级列表 |
| P1 | Modal 缺少完整键盘边界 | 焦点落入背景或关闭后丢失上下文 | 增加初始聚焦、Tab 焦点环、Escape、滚动锁定与触发点焦点恢复 |

### 验收结论

在独立 SQLite 与磁盘目录中通过 Web 真正执行“编辑项目 → 删除全文 → 删除对话 → 删除运行 → 删除项目”。第一次验收暴露运行页和对话页的删除后查询竞态，修复后全链路无 404；同时覆盖错误确认、活跃运行冲突、FTS 清理、孤立记录清理和路径删除。Vercel 公共观测站继续在服务端拒绝所有 mutation，不把临时 `/tmp` 描述成持久工作台。

## 2026-08 动态证据信号与科技感复审

### 新增参考

- [OpenScience](https://github.com/synthetic-sciences/openscience)：科学 Agent 的浏览器界面应表现为真实 workspace，把会话、文件、实验和来源组织成可操作对象。
- [React Router View Transitions](https://reactrouter.com/how-to/view-transitions)：现有 `Link`、`NavLink` 和编程式导航可以直接启用浏览器 View Transition，不需要复制路由状态。
- [MDN View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)：页面过渡的价值是保持上下文和降低感知等待，同时仍需处理焦点、阅读位置与交互边界。
- [Motion layout animation](https://motion.dev/docs/react-layout-animations)：布局动效优先使用 transform，避免通过持续改变布局属性制造卡顿；本轮未为少量微交互引入额外运行时依赖。
- [MDN prefers-reduced-motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion)：动态界面必须响应操作系统的减少动态偏好。

### 两遍设计结论

第一遍曾考虑霓虹网格、玻璃卡片和背景粒子，但这些元素与证据审计没有关系，也容易
复刻通用 AI 产品模板。第二遍把唯一视觉风险集中到“证据信号谱”：五个通道直接由
真实项目阶段计算，加载扫描只执行一次，持续脉冲只表示真实的排队或运行状态。

| 级别 | 问题 | 影响 | 处理 |
|---|---|---|---|
| P0 | 冷灰画布与规则分隔虽清晰，但缺少只属于科研证据链的识别元素 | 仍可能被看成普通后台管理页 | 首页新增真实五阶段证据信号谱，用深色仪器面形成单一视觉签名 |
| P1 | 为“科技感”直接增加循环波形会虚构系统活动 | 用户可能误判研究正在运行 | 扫描只在载入时出现；只有真实 `queued/running` 阶段持续呼吸 |
| P1 | Bahnschrift 承担全部标题，中文与混排显得过窄、过硬 | 中文标题阅读节奏不自然 | 中文标题改为系统 Display 字体，窄体与等宽字体只保留给数据和 ID |
| P1 | 页面切换瞬间跳变，固定侧栏与研究上下文割裂 | 深层项目导航感知不连续 | 主要 Link/NavLink 使用原生 View Transition，仅工作区轻微淡入位移 |
| P0 | 新动效若不尊重减少动态偏好，会形成可访问性回归 | 部分用户无法舒适使用 | 全局 reduced-motion 规则覆盖 CSS 与 View Transition，排练读取计算样式断言 |
| P2 | 新仪器面板可能挤压 390px 布局 | 手机出现横向滚动或按钮过窄 | 改为单列信号面板，排练断言文档宽度不超过视口 |

### 验收结论

真实合成 QA 项目在 1440×900 和 390×844 下完成探索与排练。证据信号、研究档案
悬停、项目证据脊柱、运行台和检索账本均可见；移动端无横向溢出；模拟
`prefers-reduced-motion: reduce` 后信号动画计算时长不超过 0.01 秒。

## 2026-08 研究工作台、仓库入口与演示验收

### 新增参考

- [GitHub README 指南](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)：仓库入口应尽早说明项目用途、价值、启动方式、帮助渠道与维护者，过长细节转移到独立文档。
- [ASReview LAB](https://github.com/asreview/asreview)：让研究者保持最终筛选决定权，保存每次决定，并把导入—筛选—监控—导出组织为连续工作流。
- [Zotero](https://github.com/zotero/zotero)：研究资料界面需要高信息密度、稳定对象身份与收藏—条目—详情层级。
- [Open WebUI](https://github.com/open-webui/open-webui)：本地运行、模型连接和响应式 Web 入口应是可独立理解的产品能力，而非隐藏在开发配置中。

### 本轮发现与处理

| 级别 | 问题 | 影响 | 处理 |
|---|---|---|---|
| P0 | 项目概览只有统计与运行列表，没有统一表达研究证据链 | 用户难以判断当前处于自动阶段还是人工门 | 新增方案—检索—筛选—证据—报告证据脊柱，并用真实状态推导完成与当前阶段 |
| P1 | 首页仍以通用项目面板组织，研究者的“下一步”不突出 | 多项目长期使用时恢复上下文较慢 | 改为今日工作与研究账本，优先指向待人工处理项目 |
| P1 | 状态、综述类型与运行事件混用内部英文值 | 中文界面可扫读性与专业感下降 | 集中映射常用状态、综述类型和事件阶段；底层枚举保持不变 |
| P1 | 普通按钮未统一声明类型 | 组件嵌入表单后可能意外提交 | 基础按钮默认 `type="button"`，显式提交由调用处覆盖 |
| P1 | 前端验收依赖人工打开页面，没有可复现演示路径 | 视觉回归与 README 截图容易脱离真实产品 | 新增 Playwright 探索、排练、录制三阶段脚本和失败诊断 |
| P1 | README 先讲架构来源，首次启动与能力边界出现太晚 | 陌生用户难以快速判断项目是否可用 | 将五分钟体验、真实截图、能力—审计依据和成熟度边界前置 |
| P2 | 旧测试说明仍使用已过时的 `unittest discover` | 贡献者无法按 CI 的真实方式复现检查 | 改为 Ruff、pytest、TypeScript、Vitest 与生产构建命令 |
| P1 | setuptools 复用历史 `build/lib`，wheel 混入已删除的前端哈希资源 | 发布包体积增大且携带不可达旧代码 | 归档缓存后干净重建，并新增源码—wheel 文件集合验证器 |

### 验收结论

使用独立合成 QA 数据库，从工作台进入项目与已完成运行，检查证据脊柱、事件流、
检索账本和产物列表。探索阶段先打印真实可见控件，排练阶段全部选择器通过后才录制
WebM；过程未启动研究、未提交筛选决定、未写入模型密钥。界面目前适合作为单机研究
工作台继续迭代，但账号权限、团队协作、正式风险偏倚工具和全文语义蕴含核验仍是边界。

## 2026-07 两阶段筛选与全文资格审计

### 新增参考

- [Cochrane Handbook Chapter 4](https://www.cochrane.org/authors/handbooks-and-manuals/handbook/current/chapter-04)：
  最终纳入以全文为基础，由至少两位研究者独立判断，并为排除报告记录一个主要原因。
- [PRISMA 2020 flow diagram](https://www.prisma-statement.org/prisma-2020-flow-diagram)：
  明确区分记录筛选、报告获取、未取得、全文资格评估、排除原因和最终纳入研究。
- [PRISMA-S](https://www.equator-network.org/reporting-guidelines/prisma-s/)：
  完整记录信息来源、检索策略与日期。
- [ASReview LAB](https://github.com/asreview/asreview)：
  保持人类为筛选决定者，界面围绕连续逐篇判断、自动保存与可修改标签组织。
- [Zotero Web Library](https://github.com/zotero/web-library)：
  使用紧凑资料工作区和检查器，而不是营销式大卡片。

### 发现与处理

| 级别 | 问题 | 影响 | 处理 |
|---|---|---|---|
| P0 | 标题筛选后直接把摘要级候选送入综合 | 不满足正式系统综述的最终全文资格判断 | 新增全文门禁，只有全文 included 进入提取 |
| P0 | 全文上传、获取失败与最终排除互相独立 | 无法还原报告从查找到决定的路径 | 新增四态获取状态和追加式事件 |
| P0 | 排除只有自由文本 | 原因汇总不稳定，双人“都排除”仍可能存在实质分歧 | 新增稳定主要排除代码；代码不同必须仲裁 |
| P1 | 标题决定修订后旧全文结论仍可能残留 | 非候选报告污染后续综合 | 清除当前全文结论，保留历史和文档 |
| P1 | “已上传”被提前计为“已评估” | PRISMA 运行计数失真 | 只有出现资格决定才计入已评估 |
| P1 | Web 无法从摘要筛选继续完成全文流程 | API 可用但研究者日常流程断裂 | 同页两阶段轨道、文件台、决定面板和流程计数 |
| P1 | v4 项目升级缺少真实旧表验证 | 用户升级可能在生产库失败 | 新增原始 v4 SQLite 到 schema v5 迁移测试 |

### 保留边界

- 当前把每个项目论文记录近似为一份报告/一项研究，尚未建立“记录—报告—研究”
  多对多去重模型；PRISMA 计数是操作辅助，不是自动合规声明。
- 系统不自动获取受限全文，也不绕过出版社访问控制。
- 下一阶段仍需正式风险偏倚工具、双人数据提取与报告级/研究级合并界面。

## 2026-07 首次用户端到端验收

### 验收场景

在独立数据目录中创建中文系统综述项目，使用内置固定语料完成计划、检索、
人工筛选、恢复、证据提取、CS 专项分析、报告、评测、全文导入、全文检索、
项目问答和可移植归档。验收数据为 5 篇候选论文、4 篇纳入、1 篇排除、
1 份全文和 1 份完成报告；同时逐页检查概览、文献库、筛选、证据、报告、
全文和对话界面。

### 新增对照依据

- [PaperQA2](https://github.com/Future-House/paper-qa)：全文先索引和切块，再检索、
  排序证据上下文并生成带引用回答。
- [OpenScholar](https://github.com/AkariAsai/OpenScholar)：科学问答把检索、
  来源落点和综合作为一体化但可评测的链路。
- [RAGChecker](https://github.com/amazon-science/RAGChecker)：分开诊断检索器与
  生成器，不使用单一总分掩盖失败环节。
- [DeepResearch Bench](https://github.com/Ayanami0730/deep_research_bench)：
  区分报告质量、有效引用数和引用准确性。
- [STORM / Co-STORM](https://github.com/stanford-oval/storm)：采用分阶段知识整理，
  并让人类在长程探索中持续参与。
- [ASReview LAB](https://github.com/asreview/asreview)：研究者是筛选决定者，
  已保存标签可修改，自动方法负责排序而不是代替最终判断。
- [Cochrane Handbook 4.6](https://training.cochrane.org/handbook/current/chapter-04)：
  最终纳排应由至少两人独立判断并预先定义冲突解决流程。
- [PRISMA 2020](https://www.prisma-statement.org/prisma-2020)：报告筛选人数、
  独立性、自动化工具和流程计数，而不是只展示完成状态。
- [Zotero 标准格式导入](https://www.zotero.org/support/kb/importing_standardized_formats)：
  RIS、BibTeX/BibLaTeX 和 CSL JSON 是文献管理互操作的基础入口。

### 本轮发现与处理

| 级别 | 实际问题 | 影响 | 处理 |
|---|---|---|---|
| P0 | 规划阶段把用户明确输入的问题替换成模型生成的通用问题 | 后续检索、报告和项目标题指向不同研究问题 | 明确问题始终保留；仅当问题等于主题时使用精炼问题，并记录策略 |
| P0 | 20% 引用可词汇评估时仍显示“对齐 100%”并获得满分 | 容易把局部代理指标误读为引用可靠性 | 新增可评估覆盖与有效对齐；评测按全部引用保守计分 |
| P1 | 离线对话能检索全文，但回答路径丢弃全文来源 | 用户无法验证全文链路是否工作 | 演示回答保留匹配全文、页码和来源侧栏 |
| P1 | Web 上传以临时 UUID 作为文档名，来源侧栏又优先显示内部文档 ID | 页码引用不可读，原文件名丢失 | 上传时保留安全化原文件名；全文来源以文件名和页码展示 |
| P1 | 筛选完成后不能重开已做决定 | 错误标签和新增全文无法触发人工修订 | 新增“复核全部决定”模式并保留原理由 |
| P1 | CLI 默认转储深层 JSON，单次验收输出超过 800 行 | 人工检查运行状态和筛选队列困难 | 默认输出研究摘要；`--json` 保留完整机器接口 |
| P2 | 报告页混用英文眉题与中文正文 | 视觉语言不一致 | 统一中文标签，补充低可评估覆盖警告 |

### 验收结论

当前版本能够在无外部 API 的情况下完整演示可恢复研究链路，也能在真实连接下
使用项目论文与全文进行来源约束问答。结构审计、词汇代理和语义蕴含仍是三种
不同能力；本轮没有把确定性词汇检查包装成事实核验。双人盲审、标准格式导入和
全文资格门已在后续版本补齐；全文级语义复核队列仍未实现。

### Web 信息架构

Web 端不采用单一聊天界面，而是围绕研究对象组织：

1. 工作台：项目、活动运行和待处理筛选。
2. 项目概览：研究问题、方案、进度与最近产物。
3. 文献库：密集列表、状态过滤和右侧论文检查器。
4. 筛选台：逐篇摘要、键盘操作、决定理由和剩余数量。
5. 运行台：八阶段流水线、事件轨迹、错误和恢复入口。
6. 证据台：证据卡、质量、复现性与 benchmark 目录。
7. 图谱：文献节点与关系、选择联动和来源详情。
8. 报告：Markdown 阅读、引用审计和产物下载。
9. 全文：上传、索引、关键词检索和页码命中。

### 仍需坚持的边界

- 图形界面不能把结构引用审计包装成事实核验。
- 演示数据必须始终标为合成数据。
- 自动筛选只能提供帮助，正式排除要保留人类决定和理由。
- 没有认证的本地 API 不能直接暴露到公网。
- 研究议程来自已检索证据的缺口，不自动等同于新颖贡献。

## 2026-08 Observatory 视觉与公网部署复审

### 设计结论

- 主题对象不是通用 AI SaaS，而是“计算机科研证据观测台”；主要受众是需要恢复项目、复核出处和继续人工门禁的研究者。
- 首页采用深蓝墨色仪器面，项目详情保留浅色研究纸面。唯一高辨识度元素是由真实五阶段数据计算的证据星图，未引入粒子背景、玻璃卡片或虚构实时活动。

| 级别 | 问题 | 处理 |
|---|---|---|
| P0 | 无认证本地 SQLite 服务不能安全直接上公网 | 单独增加 Vercel 只读入口，前后端双重阻止写操作 |
