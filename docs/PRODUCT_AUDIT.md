# 产品审计与补强记录

本文件记录 Paper Research Workbench 从研究内核走向可长期使用产品时发现的问题、依据和处理状态。每次进入新的大功能阶段，应先重新检查相关后端、数据模型、API、测试与安全边界，再更新本表。

## 2026-07 首次用户端到端验收

### 验收场景

在独立数据目录中创建中文系统综述项目，使用内置固定语料完成计划、检索、
人工筛选、恢复、证据提取、CS 专项分析、报告、评测、全文导入、全文检索、
项目问答和可移植归档。验收数据为 5 篇候选论文、4 篇纳入、1 篇排除、
1 份全文和 1 份完成报告；同时逐页检查概览、文献库、筛选、证据、报告、
全文和对话界面。

### 新增对照依据

- [PaperQA2](https://github.com/Future-House/paper-qa)：全文先索引和切块，再检索、
  排序证据上下文并生成带引用回答。
- [OpenScholar](https://github.com/AkariAsai/OpenScholar)：科学问答把检索、
  来源落点和综合作为一体化但可评测的链路。
- [RAGChecker](https://github.com/amazon-science/RAGChecker)：分开诊断检索器与
  生成器，不使用单一总分掩盖失败环节。
- [DeepResearch Bench](https://github.com/Ayanami0730/deep_research_bench)：
  区分报告质量、有效引用数和引用准确性。
- [STORM / Co-STORM](https://github.com/stanford-oval/storm)：采用分阶段知识整理，
  并让人类在长程探索中持续参与。
- [ASReview LAB](https://github.com/asreview/asreview)：研究者是筛选决定者，
  已保存标签可修改，自动方法负责排序而不是代替最终判断。
- [Cochrane Handbook 4.6](https://training.cochrane.org/handbook/current/chapter-04)：
  最终纳排应由至少两人独立判断并预先定义冲突解决流程。
- [PRISMA 2020](https://www.prisma-statement.org/prisma-2020)：报告筛选人数、
  独立性、自动化工具和流程计数，而不是只展示完成状态。
- [Zotero 标准格式导入](https://www.zotero.org/support/kb/importing_standardized_formats)：
  RIS、BibTeX/BibLaTeX 和 CSL JSON 是文献管理互操作的基础入口。

### 本轮发现与处理

| 级别 | 实际问题 | 影响 | 处理 |
|---|---|---|---|
| P0 | 规划阶段把用户明确输入的问题替换成模型生成的通用问题 | 后续检索、报告和项目标题指向不同研究问题 | 明确问题始终保留；仅当问题等于主题时使用精炼问题，并记录策略 |
| P0 | 20% 引用可词汇评估时仍显示“对齐 100%”并获得满分 | 容易把局部代理指标误读为引用可靠性 | 新增可评估覆盖与有效对齐；评测按全部引用保守计分 |
| P1 | 离线对话能检索全文，但回答路径丢弃全文来源 | 用户无法验证全文链路是否工作 | 演示回答保留匹配全文、页码和来源侧栏 |
| P1 | Web 上传以临时 UUID 作为文档名，来源侧栏又优先显示内部文档 ID | 页码引用不可读，原文件名丢失 | 上传时保留安全化原文件名；全文来源以文件名和页码展示 |
| P1 | 筛选完成后不能重开已做决定 | 错误标签和新增全文无法触发人工修订 | 新增“复核全部决定”模式并保留原理由 |
| P1 | CLI 默认转储深层 JSON，单次验收输出超过 800 行 | 人工检查运行状态和筛选队列困难 | 默认输出研究摘要；`--json` 保留完整机器接口 |
| P2 | 报告页混用英文眉题与中文正文 | 视觉语言不一致 | 统一中文标签，补充低可评估覆盖警告 |

### 验收结论

当前版本能够在无外部 API 的情况下完整演示可恢复研究链路，也能在真实连接下
使用项目论文与全文进行来源约束问答。结构审计、词汇代理和语义蕴含仍是三种
不同能力；本轮没有把确定性词汇检查包装成事实核验。正式系统综述仍缺双人盲审、
冲突仲裁、RIS/BibTeX 导入和全文级语义复核队列。

## 2026-07 前端视觉与可用性复审

### 复审依据

- [Outline](https://github.com/outline/outline)：内容优先的层级导航，避免让外壳压过文档。
- [Zotero Web Library](https://github.com/zotero/web-library)：列表、正文和检查器并列，适合研究资料高频浏览。
- [Plane](https://github.com/makeplane/plane)：紧凑而明确的状态、筛选和操作入口。
- [AppFlowy](https://github.com/AppFlowy-IO/AppFlowy)：本地优先产品的中性工作区结构。

### 发现与处理

| 级别 | 问题 | 处理 |
|---|---|---|
| P0 | 首页使用巨幅口号、装饰状态板和网格背景，更像 AI 产品模板而非研究工具 | 改为项目、论文、待筛选和运行状态组成的真实工作台 |
| P0 | 全局样式长期追加，字号、圆角、阴影和卡片规则互相覆盖 | 重建单一设计系统，统一颜色、间距、字体和交互状态 |
| P1 | 英文全大写眉题与等宽小字过多，中文阅读层级不自然 | 移除核心页面英文眉题，等宽字体仅保留代码和 ID |
| P1 | 表单与元数据字号偏小 | 正文基准提升至 15px，输入框最小高度提升至 38px |
| P1 | 对话表现为常见聊天产品，项目证据与来源边界不够强 | 改为会话、正文、来源三栏研究笔记布局 |
| P1 | 页面大量圆角卡片和装饰阴影削弱信息结构 | 常规容器使用细边框，圆角统一为 5–7px，移除常驻阴影 |
| P2 | 图谱继续使用旧版浅绿网格 | 改为中性平面画布，让节点关系承担视觉信息 |

桌面端验收覆盖工作台、模型设置、项目概览和项目对话；移动端以 390×844 视口检查导航、摘要、项目列表和横向溢出。

## 2026-07 表面层级与框架复审

### 框架选择

评估了 Primer React、Primer Primitives、Mantine、Radix Themes 和
shadcn/ui。现有项目已有稳定的语义组件与复杂研究页面，整体迁移组件库会扩大
回归范围。最终直接接入 `@primer/primitives`，使用官方 light 与
dark-dimmed 主题令牌；保留现有 React 组件和业务状态。

### 发现与处理

| 级别 | 问题 | 处理 |
|---|---|---|
| P0 | 画布、卡片、输入框和聊天正文明度过于接近，整屏视觉接近纯白 | 建立深色侧栏、冷灰蓝画布、浅内容面、白色抬升面四级层次 |
| P1 | 自定义颜色值缺少上游设计系统约束 | 接入 Primer Primitives 11.9.0，并映射前景、边框、强调色和控件状态 |
| P1 | 对话三栏虽然结构明确，但三个区域底色差异过小 | 会话列表、消息画布、来源检查器分别使用不同语义表面 |
| P2 | 引入完整 Primer React 会扩大组件迁移和包体 | 只直接使用官方 Primitives；后续新交互组件可按需引入 Primer React |

生产 CSS 增至约 221 KB、gzip 约 37 KB；入口 JavaScript 基本不变。

## 2026-07 Web 产品化审计

### 外部参考

- [Zotero Web Library](https://github.com/zotero/web-library)：采用收藏树、密集文献列表、右侧详情检查器，适合高频管理和比较元数据。
- [ASReview LAB](https://github.com/asreview/asreview)：把人工判断置于中心，逐篇筛选、保存每次决定并持续展示进度。
- [Open Knowledge Maps](https://openknowledgemaps.org/about)：图谱与文献列表联动，不把可视化做成脱离证据的装饰。
- [PaperQA2](https://github.com/Future-House/paper-qa)：重视全文索引、可复用语料库、带来源问答和缓存。
- [OpenScholar](https://github.com/AkariAsai/OpenScholar)：检索后综合科学文献，强调回答必须落到来源。
- [DeepResearch Bench](https://github.com/Ayanami0730/deep_research_bench)：报告评测不能只检查格式，还应覆盖内容质量、事实性和引用质量。
- [BrowseComp-Plus](https://arxiv.org/abs/2508.06600)：动态检索会损害公平性与复现性，评测应支持固定语料与可分解的检索指标。
- [DR³-Eval](https://arxiv.org/abs/2604.14683)：应分别衡量信息召回、事实准确、引用覆盖、指令遵循和研究深度。

### 已存在的优势

- 显式、可恢复的八阶段状态机。
- SQLite/WAL 项目库与运行事件。
- 系统综述人工纳排门。
- 稳定证据 ID、结构化引用审计和可移植产物。
- 计算机领域分类、实验字段和复现报告。
- 离线合成数据与确定性测试。

### 本轮发现的问题

| 级别 | 问题 | 影响 | 处理 |
|---|---|---|---|
| P0 | 没有面向研究者的 Web 工作台 | 只能依赖 CLI/API，无法完成日常筛选、浏览和比较 | 本轮实现 |
| P0 | API 不能读取报告、证据、图谱和产物 | 前端只能看到运行状态，不能消费科研结果 | 本轮实现 |
| P0 | Web 演示模式仍会访问在线检索器 | 无密钥或离线用户无法稳定完成首次体验 | 本轮改为内置合成语料 |
| P1 | 上传一次性读入内存且没有大小上限 | 大文件可能耗尽本地服务内存 | 本轮改为分块写入并限制体积 |
| P1 | API 返回文档内部绝对路径 | 不必要地暴露本机存储结构 | 本轮对外响应移除内部路径 |
| P1 | 没有可下载的项目归档与单项产物接口 | 审计、交接和外部分析不顺畅 | 本轮实现安全下载 |
| P1 | 评测主要是结构与字段完整性 | 无法证明事实准确或引用蕴含 | 保留明确边界，下一阶段加入语义引用核验 |
| P1 | 没有混合检索、向量索引和全文证据定位 | 摘要级综合仍是主要路径 | 下一阶段 |
| P1 | 单进程任务队列重启后不恢复 | 长任务在服务升级时脆弱 | 下一阶段设计持久任务租约 |
| P2 | 无项目编辑、归档和协作权限 | 团队长期使用能力有限 | 团队版阶段 |
| P2 | 文献关系图主要来自元数据启发式 | 不能替代真实引用网络 | 后续接入 OpenAlex/S2 引用边 |
| P2 | 暂无 RIS/BibTeX/Zotero 批量导入 | 迁移现有文献库成本较高 | 下一阶段 |
| P2 | 暂无 PDF 图表、公式和版面理解 | 多模态 CS 论文证据会丢失 | 后续多模态阶段 |

### Web 信息架构

Web 端不采用单一聊天界面，而是围绕研究对象组织：

1. 工作台：项目、活动运行和待处理筛选。
2. 项目概览：研究问题、方案、进度与最近产物。
3. 文献库：密集列表、状态过滤和右侧论文检查器。
4. 筛选台：逐篇摘要、键盘操作、决定理由和剩余数量。
5. 运行台：八阶段流水线、事件轨迹、错误和恢复入口。
6. 证据台：证据卡、质量、复现性与 benchmark 目录。
7. 图谱：文献节点与关系、选择联动和来源详情。
8. 报告：Markdown 阅读、引用审计和产物下载。
9. 全文：上传、索引、关键词检索和页码命中。

### 仍需坚持的边界

- 图形界面不能把结构引用审计包装成事实核验。
- 演示数据必须始终标为合成数据。
- 自动筛选只能提供帮助，正式排除要保留人类决定和理由。
- 没有认证的本地 API 不能直接暴露到公网。
- 研究议程来自已检索证据的缺口，不自动等同于新颖贡献。

## 2026-07 Agent 连接与证据对话审计

### 新增参考

- [Open WebUI](https://github.com/open-webui/open-webui)：把 Agent 建模为基础模型之上的指令、知识与工具配置。
- [LibreChat Agents](https://www.librechat.ai/docs/features/agents)：在模型入口选择 Agent，并保留多提供商连接。
- [AnythingLLM](https://github.com/Mintplex-Labs/anything-llm)：把文档、对话和 Agent 状态限制在 workspace。
- [OpenAI Knowledge Retrieval](https://github.com/openai/openai-knowledge-retrieval)：拆分摄取、检索、综合、引用 UI 与评测。
- [PaperQA2](https://github.com/Future-House/paper-qa)：对全文块检索、重排和证据上下文进行独立处理。

### 本轮发现与处理

| 级别 | 问题 | 处理 |
|---|---|---|
| P0 | Web 不能接入模型，也不能在运行时选择 Agent | 新增进程级连接、五种科研 Agent 和运行配置 |
| P0 | 没有项目级问答与消息历史 | 新增 conversations/messages、证据回答和来源侧栏 |
| P1 | Web 密钥若持久化会进入数据库或备份 | 密钥仅驻留进程内存，所有响应脱敏 |
| P1 | 对话论文上下文按 ID 截断，不随问题变化 | 新增中英文词项相关性重排 |
| P1 | 模型可能输出项目中不存在的引用 ID | 新增未知引用检查并在回答中显式告警 |
| P1 | 入口 JavaScript 超过 500 KB | 改为页面级懒加载，入口降至约 262 KB |
| P1 | 仍缺少向量/关键词混合全文检索和重排评测 | 保留到下一阶段，不把词项代理指标称为语义检索 |
| P2 | 会话连接随进程重启失效 | 本地版作为安全取舍；团队版需外部 secrets manager |

## 2026-07 文献互操作与导入审计

### 外部参考

- [Zotero Translation Server](https://github.com/zotero/translation-server)：把网页识别、标识符检索、格式导入和格式导出分成清晰边界。
- [ASReview LAB](https://github.com/asreview/asreview)：导入后隐藏重复项，但保留决定与可恢复的导出语义。
- [JabRef](https://github.com/JabRef/jabref)：在导入时检测重复，并允许后续补全、比较和合并元数据。
- [Crossref Citation Formatting Service](https://www.crossref.org/labs/citation-formatting-service/)：采用 CSL JSON 的 `container-title`、`issued.date-parts` 与 DOI 等标准字段。

### 发现与处理

| 级别 | 问题 | 处理 |
|---|---|---|
| P0 | 已有 Zotero/EndNote/JabRef 文献无法进入项目 | 新增 RIS、BibTeX/BibLaTeX 与 CSL JSON 导入 |
| P0 | 逐条写入会在中途错误后留下半批数据 | 整批解析后在单个 SQLite 事务中入库 |
| P0 | 通用 upsert 可被后续不完整检索结果覆盖作者、摘要和引用量 | 改为无损补全，引用量取最大值 |
| P1 | 重复导入可能覆盖人工筛选状态或改变证据 ID | 只附加新论文，既有项目关联与状态保持不变 |
| P1 | 模糊标题合并可能把不同论文静默合并 | 只使用规范化 DOI、arXiv ID 或精确规范化标题 |
| P1 | 大文件与恶意重复记录可能放大内存和数据库压力 | 同时限制上传字节与解析前记录总数 |
| P1 | 非 UTF-8 导出在 Windows 研究流程中常见 | 支持 BOM UTF-16 与 Windows-1252 回退并给出警告 |
| P2 | 文献列表多出空列且选中态类名不一致 | 改为三列布局并恢复可见选中反馈 |

### 保留边界

- 当前导入器覆盖常用核心字段，不承诺完整实现全部 BibLaTeX 宏、Zotero 附件路径或自定义字段。
- 精确标题兜底仍可能合并同名出版物；系统不使用高风险的静默模糊去重。
- “兼容 Zotero”指标准导出文件互操作，不代表已接入 Zotero Web API 或双向同步。
